  <action>
In `bin/cli.js`:

1. Import `claimLock` and `releaseLock` from `../src/services/coordination.js` (dynamic import alongside the other imports at the top).

2. After the `fastify.listen()` port-fallback loop succeeds (after `const actualPort = fastify.server.address().port;`), BEFORE the "running at" message:
   - Call `claimLock(db, 'server', process.pid, 'web', actualPort)`
   - If `!result.claimed`:
     - Build URL: `http://127.0.0.1:${result.owner.port}`
     - Print: `Server already running at ${url} (PID ${result.owner.pid})\n`
     - Close fastify: `try { await fastify.close(); } catch (_) {}`
     - Close db: `try { db.close(); } catch (_) {}`
     - `process.exit(0)` (clean exit, not an error)
   - If `result.claimed`: continue with existing "running at" message and browser open

3. Update the existing SIGINT/SIGTERM handler to release the server lock:
   - Add `releaseLock(db, 'server', process.pid);` BEFORE the existing `fastify.close()` and `db.close()` calls
   - The releaseLock call is synchronous (node:sqlite DatabaseSync), so it runs reliably in the signal handler

4. Remove the port-fallback loop (the `for (let attempt = 0; attempt < 10; attempt++)` block). Replace it with a single `fastify.listen({ port: DEFAULT_PORT, host: '127.0.0.1' })` call wrapped in try/catch. If EADDRINUSE, the server lock check below will determine if it's our app or something else:
   - Actually, keep the port-fallback loop AS-IS. The lock check after listen() is the coordination mechanism. If another cctimereporter is on port 3847, the new instance might bind to 3848, but then the lock check will detect the conflict and shut down. This is the correct order: listen first (to get a port), then check lock.

Important behavioral notes:
- The server lock is claimed AFTER listen() succeeds, not before. This means the port is already bound.
- If claim fails (another server is live), we close the just-opened fastify instance and exit.
- The port-fallback loop stays because it handles non-cctimereporter port conflicts (e.g., another app on 3847). The DB lock handles cctimereporter-vs-cctimereporter conflicts.
- Do NOT open the browser if the lock claim fails (we're exiting).
