```javascript
/**
 * Detect a slash command in a user message.
 * Returns the command name without leading slash (e.g. 'clear', 'rename'), or null.
 */
function detectCommand(rawMsg) {
  if (rawMsg?.type !== 'user' || rawMsg?.isMeta) return null;
  const text = extractContentText(rawMsg)?.trim();
  if (!text) return null;

  // XML format: <command-name>/clear</command-name>...
  const parsed = parseCommandXml(text);
  if (parsed) {
    const nameWithSlash = parsed.split(' ')[0]; // "/clear" or "/gsd:execute-phase"
    return nameWithSlash.startsWith('/') ? nameWithSlash.slice(1) : nameWithSlash;
  }

  // Plain text format: "/command" or "/command args"
  const plainMatch = text.match(/^\/([a-zA-Z][a-zA-Z0-9:_-]*)/);
  if (plainMatch) return plainMatch[1];

  return null;
}
```

Create `src/server/routes/timeline-contract.md` documenting the segment-aware response shape for `GET /api/timeline`. This contract is the interface that Phases 20, 21, and 22 code against.

The document must include:

1. **Current vs v0.6.0 shape**: Show that `sessions[]` becomes `segments[]` on each project object.

2. **Segment object fields** (all fields from current session object, plus new ones):
   - `segmentId` (string): `"${sessionId}:${N}"` format, e.g. `"abc123:0"`. Used as rendering key in v-for.
   - `sessionId` (string): Original session UUID. Used for PATCH /api/sessions/:id and GET /api/sessions/:id/messages.
   - `segmentIndex` (number): 0-based index within the session.
   - `isSplit` (boolean): `true` if the parent session has more than one segment. `false` for unsplit sessions.
   - All existing fields preserved: `startTime`, `endTime`, `continuesFromPrevDay`, `continuesIntoNextDay`, `workingTimeMs`, `idleGaps`, `ticket`, `branch`, `summary`, `firstPrompt`, `customTitle`, `userLabel`, `userTicket`, `messageCount`, `userMessageCount`, `forkCount`, `realForkCount`.

3. **Behavioral rules**:
   - Sessions with no `/clear` produce exactly one segment (segmentIndex 0, isSplit false)
   - The `/clear` message is excluded from both adjacent segments (no double-counting)
   - Overnight clipping happens BEFORE segment splitting
   - Each segment's `ticket` and `branch` are derived from only that segment's messages
   - `summary`, `firstPrompt`, `customTitle`, `userLabel`, `userTicket` come from the parent session (shared across all segments of the same session)
   - `messageCount` and `userMessageCount` reflect only that segment's messages
   - `workingTimeMs` and `idleGaps` are scoped to that segment's time range

4. **Segment ID resolution** for existing endpoints:
   - `PATCH /api/sessions/:id` — if `:id` contains `:`, strip the suffix to get sessionId
   - `GET /api/sessions/:id/messages` — if `:id` contains `:`, strip the suffix; return messages for the full session (or optionally filter by segment range)

5. **Example JSON** showing a project with one unsplit session and one session split into 2 segments.

6. **`totalSessions` field**: Retains session count (not segment count) for backward compatibility. Add `totalSegments` as new field.

Keep it concise -- this is a reference for Claude implementors, not user-facing documentation.
