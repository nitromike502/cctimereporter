# Phase 23 Plan 01: Backend Fork Segments

## Objective

Extend the timeline API to return computed fork segment data for sessions that have real forks.
The `GET /api/timeline` response will include a `forkSegments` array on each session object,
enabling the frontend to render fork bars without any further processing.

## Context

- @src/server/routes/timeline.js — timeline route to modify
- @src/db/schema.js — schema reference (v7 with fork_branch_id)

## Tasks

### Task 1: Add computeForkSegments() and integrate into timeline route

type="auto"

Add a `computeForkSegments()` helper function to `src/server/routes/timeline.js` and integrate it
into the timeline request handler.

**Implementation details:**

1. Add a prepared statement for the fork segment batch query:
   ```sql
   SELECT session_id, fork_branch_id,
          MIN(timestamp) AS start_time,
          MAX(timestamp) AS end_time,
          COUNT(*) AS message_count
   FROM messages
   WHERE session_id IN (/* placeholders */)
     AND fork_branch_id IS NOT NULL
     AND type IN ('user', 'assistant')
     AND timestamp IS NOT NULL
   GROUP BY session_id, fork_branch_id
   ```
   Note: SQLite's `node:sqlite` driver does not support array binding for IN clauses via
   prepared statements. Build the query dynamically at request time using the session IDs
   of sessions with `real_fork_count > 0`.

2. Add `computeForkSegments()` function that:
   - Takes raw DB rows for a single session and day boundary strings
   - Clamps start/end to day boundaries (same as overnight session clamping)
   - Returns `{ forkBranchId, startTime, endTime, messageCount }[]`

3. In the request handler:
   - After building the sessions list, collect session IDs where `real_fork_count > 0`
   - If none exist, skip the fork query entirely (no DB overhead for common case)
   - If some exist, run the dynamic batch query, group rows by session_id
   - Attach `forkSegments` array to each session object (empty array for sessions with no real forks)

4. Working time policy: fork branch messages are currently included in working time computation
   (via the existing `messageStmt` query which returns all messages by session_id).
   Keep this behavior and document it with a comment near the fork query:
   "Fork branch messages are intentionally included in working time — forks represent
   parallel exploration within the same work session."

**Done criteria:**
- `GET /api/timeline` response includes `forkSegments` on every session object
- Sessions with `real_fork_count = 0` have `forkSegments: []`
- Sessions with real forks have segments with `{ forkBranchId, startTime, endTime, messageCount }`
- Fork segment timestamps are clamped to day boundaries
- No DB query is issued when no sessions on the day have real forks
