<objective>
Extend the messages API to support timestamp-range filtering for bucket drill-down.

Purpose: The frontend needs to fetch messages within a specific time bucket (e.g., 2:10-2:15 PM) when the user double-clicks a point on the Per Message line chart. The existing `/api/sessions/:id/messages` endpoint only returns head/tail truncated messages for the whole session. This plan adds `from` and `to` query params that return all messages in a time window, with token counts on assistant messages for inline display.

Output: Updated sessions service and messages route that accept optional `from`/`to` ISO timestamp query params. When provided, returns all messages in the range with no truncation and includes `outputTokens` on assistant messages.
</objective>

<task type="auto">
  <name>Task 1: Add timestamp-range query mode to sessions service</name>
  <files>src/services/sessions.js</files>
  <action>
Add a new prepared statement `timeRangeStmt` in the `createSessionsService` factory that selects messages within a timestamp range. The query should:

```sql
SELECT uuid, type, content, timestamp, is_fork_branch, fork_branch_id,
       output_tokens
FROM messages
WHERE session_id = ?
  AND content IS NOT NULL
  AND timestamp >= ?
  AND timestamp < ?
  AND (fork_branch_id IS NULL OR fork_branch_id = '')
ORDER BY timestamp ASC
```

Key points:
- Include `output_tokens` column (only meaningful for assistant messages; will be null for user messages).
- Filter to primary branch only (`fork_branch_id IS NULL OR fork_branch_id = ''`) — same as `primaryBranchStmt`.
- No sidechain filter needed here; this is a content-display query, not a token-aggregation query.

Extend `getMessages(sessionId, opts)` to accept optional `{ from, to }` in the options object. When both `from` and `to` are provided:

1. Still check session exists via `sessionExistsStmt`.
2. Run `timeRangeStmt.all(sessionId, from, to)`.
3. Map rows with `mapRow` but ALSO include `outputTokens: r.output_tokens ?? null` on each message.
4. Return `{ messages: allMessages, totalCount: allMessages.length, skipped: 0, isBucketView: true }`.
5. Do NOT apply head/tail truncation when `from`/`to` are present. The CONTEXT.md says "Same pattern as existing modal: first 10 + last 10 messages with 'N messages skipped' divider for large intervals" — BUT the research correctly notes buckets are typically 1-30 minutes, yielding small message sets. Apply head/tail truncation to bucket views as well for safety (the same HEAD_COUNT/TAIL_COUNT logic). Actually, re-reading CONTEXT.md section 3: "Head/tail truncation. Same pattern as existing modal: first 10 + last 10 messages with 'N messages skipped' divider for large intervals." So DO apply the same truncation. Use the same head/tail logic as the primary branch path.

The `mapRow` function currently does NOT return `output_tokens`. For the time-range path, create a `mapRowWithTokens` variant that adds `outputTokens: r.output_tokens ?? null`. This avoids changing the response shape for existing callers.

When `from`/`to` are NOT provided, behavior is completely unchanged (existing code paths untouched).
