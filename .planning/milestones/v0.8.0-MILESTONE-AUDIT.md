### Flow 3: Agent start_server → gets URL

**Status: COMPLETE (with one non-blocking design note)**

- `start_server` checks `_fastifyInstance` (in-process guard), then checks DB lock for another process.
- If no server running: starts Fastify with port fallback (3847 → 3856), claims server lock, stores `_fastifyInstance`.
- Returns `{ status: 'started', url: 'http://127.0.0.1:3847' }`.
- Subsequent calls return `{ status: 'already_running', url: ... }` via `_fastifyInstance` check.

**Design Note (non-blocking):** `start_server` does not check the return value of `claimLock` at line 100 of `src/mcp/tools/action.js`. If a TOCTOU race occurs (another process claims the lock between the check at line 69 and the `claimLock` call at line 100), the MCP process will have an orphaned Fastify instance listening with no lock entry. In practice, this race is extremely narrow (two MCP processes calling `start_server` simultaneously against an empty lock table), and the orphaned instance remains functional — it just won't appear in `server_status` or be stoppable by `stop_server` from other processes. The `_fastifyInstance` module guard ensures the owning process can still stop it.

### Flow 4: Agent stop_server → server terminates → lock cleared

**Status: COMPLETE**

- `stop_server` checks DB lock.
- If no lock or dead PID: returns `{ status: 'not_running' }` (tested live — works cleanly with no errors).
- If lock owned by this MCP process: closes `_fastifyInstance`, releases lock, returns `{ status: 'stopped' }`.
- If lock owned by another process: sends SIGTERM, waits 300ms, releases lock via `releaseLock(db, 'server', lock.pid)`.

**Double-release safety confirmed:** The serve command's SIGTERM handler also calls `releaseLock`. Since `releaseLock` is `DELETE WHERE lock_name = ? AND pid = ?`, double-release is a no-op. Verified live.

- Cross-process: DB lock prevents concurrent imports from different processes (WAL mode + busy_timeout=5000ms confirmed set).
- Same-process: In-memory `_importState` guard prevents double-call within one process.

## Findings Requiring Attention

### Finding 1: start_server race — claimLock return value not checked (LOW RISK)

**File:** `src/mcp/tools/action.js`, line 100  
**Description:** After `fastify.listen()` succeeds, `claimLock()` is called but its return value is not checked. If another process wins the lock in the TOCTOU window (between the lock check on line 69 and the INSERT on line 100), the Fastify instance will be orphaned — running and serving traffic but invisible to `server_status` and `stop_server` from other processes.

**Risk:** Extremely low in practice (requires two MCP processes racing on an empty lock table). The owning process's `cleanupMcpServer` on exit will still close the orphan. No data loss or crash risk.

**Fix:** Check `claimLock` return value; if not claimed, close the just-started Fastify and return the winner's URL instead.

```js
// After listen succeeds:
const lockResult = claimLock(db, 'server', process.pid, 'mcp', actualPort);
if (!lockResult.claimed) {
  try { await fastify.close(); } catch (_) {}
  return { content: [{ type: 'text', text: JSON.stringify({ 
    status: 'already_running', 
    url: `http://127.0.0.1:${lockResult.owner.port}` 
  }) }] };
}
_fastifyInstance = fastify;
```

### Finding 2: Inconsistent maxAgeDays defaults across callers (DESIGN NOTE)

**Description:** The three callers of `runImport` use different default windows:
- Web API (`POST /api/import`): `maxAgeDays = undefined` → `importAll` defaults to **30 days**
- CLI `import` command: `--days 2` default → **2 days**
- MCP `trigger_import`: `max_age_days ?? 2` → **2 days**

The web API and programmatic callers behave differently with no explicit flag. This is a design inconsistency rather than a bug — the web API's 30-day default was the original behavior and changing it would be a behavior change for existing users.

**Recommendation:** Document in MCP tool description that default is 2 days (already done). Consider aligning `POST /api/import` to also default to 2 days in v0.8.0 to make behavior consistent across all callers.

### Finding 3: _resetImportState exported but no tests (LOW RISK, TECH DEBT)

**File:** `src/services/import.js`, line 87  
**Description:** `_resetImportState` is exported for test teardown but no test files exist in this codebase. The export is harmless but represents a gap if integration tests are planned for v0.8.0.
